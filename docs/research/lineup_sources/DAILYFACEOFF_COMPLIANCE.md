# DailyFaceoff collection: access method, compliance risks, fallback (2026-10-25)

## What the repository does with DailyFaceoff (DFO)
| use | code | frequency | what is stored |
|---|---|---|---|
| line combinations, PP/PK units, injury status | `data/context.py::_append_lines`, `data/lines.py` | every capture-worker `context` job (hourly-ish), teams with a game today | rows in `context/lines` (player, unit, slot, source label, DFO `updatedAt`, our observation time) |
| projected/confirmed starting goalies | `data/goalies.py::fetch_dailyfaceoff` | same job | rows in `context/goalie_observations`, **raw page JSON in `context/dailyfaceoff_raw`** (sportsbook fields stripped only from derived rows) |
| projection-foundation live capture (second, independent fetch of both DFO pages) | `research/projection_foundation/nhl/live/fetch.py` | each projection run | rows in `projection-data` |
| copies of fetched pages | `docs/probe/samples/dailyfaceoff_goalies*.html` (220 KB); `scripts/probe_sources.py` (`probe.yml`) is configured to save such samples (`sample_html`) | one-off probes | full page HTML committed to the repository |

All of it lives in a **public** repository (`data-archive`, `workload-shadow-data`, `player-minutes-data` and `main` are public branches).

## Findings
1. **Spoofed User-Agent: removed everywhere.** Until now DFO (and the history pulls) were requested with a fake Chrome / `Mozilla/5.0` User-Agent from five places: `data/context.py` (lines), `data/goalies.py` (goalies), `data/history.py` (history pulls), the projection-foundation live capture (`research/projection_foundation/nhl/live/fetch.py`, both DFO pages) and the probe scripts (`scripts/probe_sources.py`, `scripts/probe_player_sources.py`). An independent review found the last three after the first version of this change; all are fixed and a repository-wide test now fails if a browser User-Agent reappears. `fetch()` also ignores any caller-supplied User-Agent, so it cannot be reintroduced by a call site. The audit (`SOURCE_AUDIT_2026-10-25.md`) shows DFO answers the identifying agent with HTTP 200 and the full page, including through the pipeline's own fetch and parsers, and robots.txt allows those paths, so the impersonation was not needed to obtain access. Scope of that evidence: DailyFaceoff only; the history-pull hosts (MoneyPuck files, nhle.com) were not requested with the production paths, so the claim is not made for them (the same hosts are already fetched elsewhere with the identifying agent: `data/moneypuck.py`, `data/nhl_api.py`). It is gone (`BROWSER_HEADERS` deleted; a test fails if a browser User-Agent reappears). **Impact on the lineup feed: none observed** (the production fetch and parsers returned usable lines and goalie pages once from a runner; the first production `context` and projection-foundation runs after the merge are the live confirmation). The first production `context` run after the merge is the confirmation; if DFO ever starts refusing the identifying agent, the correct behaviour is to treat that as a refusal, not to disguise the client (the pipeline already degrades to shift-derived deployment `RECENT_SHIFTS` and to the other goalie sources).
2. **Access method:** plain HTTP GET of the public HTML page, parsing the embedded Next.js `__NEXT_DATA__` JSON. No login, no API key, no rate-limit evasion; robots.txt allows the paths; the request rate is one GET per team page per capture cycle for teams playing that day.
3. **Terms of use: not located.** Neither the footer links the tool followed nor `/terms-of-service` produced a terms document (privacy policy only). Absence of found terms is not permission.
4. **Redistribution risk (the larger open question).** The repository republishes DFO-derived material publicly: parsed lines/units (`context/lines`, copied into the prospective record branches as inputs), **raw page JSON** (`context/dailyfaceoff_raw`) and sample HTML files. Line combinations are facts about team deployment, but the raw page bodies and wholesale copies are the part most likely to need permission. This PR does not delete anything (the archive is audit evidence); the proposals below are for the owner.

## Proposals (owner decisions)
1. **Ask DFO for permission** to collect line/goalie pages at the current rate and to store derived rows, with an identifying contact in the User-Agent. Until an answer, treat permission as unclear.
2. **Minimise while unclear (reduced-function fallback, no loss of the production feed):** stop writing the *raw* DFO page bodies to the public archive (`context/dailyfaceoff_raw`) — parsed rows already carry what the models use — and stop committing page HTML under `docs/probe/samples/`. Existing history would stay as audit evidence unless you decide otherwise.
3. **If permission is refused:** switch `context/lines` and the DFO goalie feed off; production continues with shift-derived deployment and NHL-published goalie data, at the cost of power-play-unit, scratch and early starting-goalie information. Impact to document then: line/PP inputs fall back to `RECENT_SHIFTS`; starter confirmation arrives only when the NHL publishes it (measured by the lineup probe).
4. Do not enable the NHL HTML game-sheet probe: nhl.com's terms prohibit automated compilation of site content (see the audit).

Nothing in this change disables or alters a feed.
